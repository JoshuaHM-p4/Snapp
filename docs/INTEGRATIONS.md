# Integration boundaries — company workflow and Testnet demonstration

The target is a Proyekto-connected owner-approved cutoff pay-run and payment-transparency layer. The web/API remains a milestone-based preview demo; **no live Proyekto integration, bank integration or approved payroll-run snapshot is implemented or verified**. Separate local CLI tooling implements a controlled single-item Noir Testnet experiment with exact signed consent, a durable SQLite operation journal and reconciliation. That is not an authenticated payroll web workflow. Neutral temporary branding and Stellar Testnet-only hackathon scope remain.

**Reference basis:** supplied *Velo x Noir Agentic Payment Hackathon — Builder Handbook* updated Nov 5, 2026, [Noir contract reference](https://github.com/noirx402/noir/blob/main/docs/contracts.md), and current [Velo release scope](https://github.com/Velo-Ecosystem-Collection/Velo/blob/main/packages/velo-sdk/README.md#release-scope). Documentation and source review are not live SDK/provider validation.

## Proyekto and compensation boundaries — target only
Proyekto already supplies projects, tasks, docs, progress, roadmaps/Gantt and invoicing. Snapp should link/import those references with provenance rather than duplicate the system; no connector is delivered here. For cutoffs **1–15** and **16–end-of-month**, consolidate employee/project hours with actual outputs and versioned client feedback. The boss manually reviews hours and retains final release authority.

Milestones group deliverable evidence. Client evaluation records output version, comments, revision requests and acceptance identity/time/version, not invented objective ratings. Client acceptance or invoice collection does not automatically determine eligibility for hours-based employee pay: applicable agreements and legal obligations govern. Keep employment/hourly compensation distinct from fixed-fee milestone contracting.

Employees need their own calculation statement (reviewed hours, applicable rates, allocations, explained adjustments and total), a discrepancy channel and access to **their own compensation only**. These are pending features, not properties of the public fixture API.

## Company bank path — recommended, not implemented
The primary pain is repeated recipient/amount copying and separately authorizing each transfer. Recommend generating a file in the **chosen corporate bank's supported format**, after verifying account eligibility, schema, recipient validation, upload limits, approval controls and recipient-level result reporting with that bank. For example, [BPI BizLink](https://www.bpi.com.ph/institutional-banking/cashflow-management/bizlink) already advertises transaction-file upload and approval controls; [Sprout payroll](https://sprout.ph/product/payroll-management/) offers payslips/timekeeping/bank-file generation. Differentiate through Proyekto-linked review and traceability, not by claiming to invent payroll or bulk banking.

No bank file/export or API is implemented or live-tested here. A bank API is only a future option after provider capability is verified. Do not automate bank UI/OTP, bypass bank approval or promise one OTP; the bank's controls remain authoritative. A file upload/approval is not proof that every recipient succeeded.

## Required run/execution boundary — pending
- Boss approves an immutable cutoff run revision binding exact recipient, amount, currency/asset and item identity. Any changed item, recipient, amount, hours or adjustment requires reapproval; execute only that approved snapshot.
- Reserve each item transactionally with a unique execution identity before external submission, persist provider/chain identity and reconcile recipients individually. A run may be partially successful; failed, unknown, submitted and confirmed results must remain distinguishable. Unknown outcomes require reconciliation, never blind retry.
- Enforce verified recipients/allowlisting **and cumulative approved-run spending/reservations app-side**. Noir only caps per payment/asset/expiry; neither an allowlist nor a cumulative cutoff cap is in its policy. Contract nonce replay protection is not business-level item deduplication: a new authorization nonce could repeat the same intended payment.
- Employee statements, approval audit records and reconciliation must refer to the same immutable revision. JSON milestone fixtures do not implement these guarantees. The local experiment journal reserves one approved item and cumulative device spending within one intact journal; it does not implement cutoff-run snapshots or web/payroll authorization.

### Durable identity, recovery and proof
The canonical journal is repository-root `.data/noir-testnet.sqlite` regardless of workspace cwd; all roles use that same trusted local checkout/journal. Absolute `--manifest` and deliberate `--db` paths are simplest across role shells. Relative paths resolve against npm's original invocation directory (`INIT_CWD`), or current cwd for direct Node invocation. An explicit database override must remain consistent; live in-memory storage is prohibited.

An immediate SQLite transaction holds approval/budget validation, preparation/signing and the reservation; the public hash/operation/nonce commits **before broadcast**. No secrets or signed XDR are stored. `prepared`, `unknown`, `succeeded` and `failed` distinguish reserved identity, unresolved outcome, confirmed transaction success and confirmed failure. Prepared/unknown/succeeded authorizations count toward cumulative device limits in the journal. An experiment/kind is single-use with no reset/retry/replacement-nonce path, including failed operations.

On any post-persistence submission error, reconcile the same hash; do not replay. `reconcile` reads transactions and matches relevant SDK events without signing/sending. `NOT_FOUND`, retention gaps and network errors leave the outcome unknown and reservation intact, not safe to resend. This is a **one-intact-journal** guarantee, not cross-copy/deletion or multi-host deduplication. A second journal/checkout cannot safely substitute for the original.

`evidence` returns local JSON separating submitted hashes from confirmed transaction/ledger metadata and matched contract event evidence, with genuine `https://stellar.expert/explorer/testnet/tx/<hash>` links. Missing events remain incomplete evidence even when the transaction is confirmed. Preserve authorization (`payment.authorized`) and aggregate merchant claim (`payment.claimed`) evidence separately. Authorization alone is not receipt; an aggregate claim is not one claim per item, a PHP bank transfer or legal wage settlement.

## Velo — separate optional client collection
The repository's server package **declares `@carts1024/velo-sdk: "alpha"`**; the Noir work did not upgrade it. The root lockfile records its resolved dependency; installation is not live compatibility/provider validation. Current upstream README describes stable **`1.0.0` / `latest`**, but its [release scope](https://github.com/Velo-Ecosystem-Collection/Velo/blob/main/packages/velo-sdk/README.md#release-scope) explicitly remains **Stellar Testnet only, no Mainnet, no settlement and no external payment provider**. Stable package status does not make real fiat collection or bank payroll available.

Existing server adapter usage (not a live compatibility validation):
- `new Velo({apiKey, environment:'testnet'})` on server only.
- `velo.checkout.sessions.create({amount:'2.5',asset:'native',description,successUrl,cancelUrl})`.
- `velo.paymentIntents.retrieve(paymentIntentId)` for observed final state; durable server reconciliation is not implemented.
- `Velo.webhooks.verify({payload: rawBody.toString(), signature, secret})` before processing. Known upstream issue: both `0.1.0-alpha.4` and `1.0.0` parse the body only after the HMAC check and require every `project` field to be a string, which Velo's live deliveries do not satisfy (`Invalid webhook event: project fields must be strings`), so a genuine signed event is thrown. For that shape-only failure the server re-verifies the same HMAC scheme with a constant-time compare and accepts a minimal `{id,type,paymentIntent.id/txHash}` event; signature failures are rethrown unchanged. Worth reporting to Velo. The handler then dedupes on `event.id` in SQLite and sets collection status only from `paymentIntents.retrieve`; terminal statuses never regress. This is a client-collection record, not invoice settlement, Noir funding or employee pay.

This optional collection path is separate from employee payout and Noir escrow funding. PHP invoice amounts do not establish Testnet asset equivalence. Do not mark paid from a redirect or invent a Velo-to-bank/escrow funding bridge.
